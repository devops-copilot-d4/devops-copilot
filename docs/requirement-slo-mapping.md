# Requirement -> SLO -> Metric -> Recovery Mapping

This document explains the data model connecting business requirements to
technical recovery, for use in the report and viva.

## Flow
1. **Requirement** - a natural-language statement from a stakeholder
   (e.g. "checkout should feel fast and reliable").
2. **Requirement Analyzer (LLM)** - converts this into a draft **SLO**:
   a metric name, comparator, threshold, and unit
   (e.g. p95 latency < 300ms).
3. **Metric** - the concrete Prometheus query backing that SLO
   (e.g. `histogram_quantile(0.95, http_request_duration_seconds_bucket)`).
4. **SLO** - links Requirement + Metric + threshold; status is
   `met` / `violated` / `unknown`, refreshed by polling Prometheus.
5. **Incident** - created when an SLO is violated (or predicted to be).
   Root cause is generated by the LLM from logs/events/metrics.
6. **RecoveryAction** - a chosen remediation (restart/rollback/scale),
   with an LLM-generated explanation and, for high-impact actions, a
   human approval gate before execution.
7. **Post-recovery verification** - after the K8s action runs, the SLO is
   re-checked. `requirementVerified` is only true if the *business*
   requirement is restored, not just if the pod is running again.

## Why trend-based prediction instead of trained ML
Given the team's timeline (11 weeks, Thu-Sun only) and the lack of a large
historical dataset, failure *prediction* uses a lightweight
threshold-trend heuristic (e.g. "error rate rising X%/min -> will breach
in Y minutes") rather than a trained model. This keeps the "prediction"
claim honest and demoable, while leaving room to mention trained ML as
future work in the report.

## Why rule-based recovery decisions instead of a trained RL agent
The requirement-aware recovery layer uses a rule-based mapping from
(root cause + business impact) to an action type, with the LLM providing
the natural-language justification. This is realistic for the timeline
and still delivers the core novelty: recovery decisions are informed by
*business* impact, not just infrastructure severity.
